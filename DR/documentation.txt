--------------------------------------------------------------------------------
00. OVERVIEW
--------------------------------------------------------------------------------

The base algorithm is a distributed Douglas-Rachford (DR) splitting method
that clears a peer-to-peer energy market, formulated as a Generalized Nash
Equilibrium Problem (GNEP). It is exact, distributed (one hop of
communication per iteration, nothing more), and provably convergent on its
own.

The contribution is a learned, additive perturbation -- one extra term
added to the DR update at every iteration, produced by a graph neural
network (GNN) -- designed to reduce the number of iterations needed to
reach the equilibrium. Three requirements had to hold simultaneously:

  - Plain DR must remain distributed and convergent, unmodified.
  - DR + perturbation must ALSO be distributed and convergent -- for ANY
    weights the network ends up with, trained well or badly.
  - Training is the only centralised step. Every prosumer runs inference
    locally, using only what it has seen over its own one-hop links.

The rest of this document walks through the system in the order it
actually executes: the market model, the base algorithm, the theorem that
makes the perturbation safe, the network that produces it, how it is
wired into the DR update, how it is trained, and how the whole pipeline
fits together -- closing with the current empirical picture, including
its open problem.


--------------------------------------------------------------------------------
01. THE MARKET MODEL
--------------------------------------------------------------------------------

The distribution network is a connected graph G=(N,E). Each prosumer n
controls three decision variables:

  D_n     flexible demand
  G_n     controllable local generation (flexibility activation)
  q_mn    bilateral trade with neighbour m: positive = buying from m,
          negative = selling to m

Plus one fixed (non-decision) parameter: DeltaG_n >= 0, a renewable
injection.

Each prosumer's LOCAL FEASIBLE SET is a box plus one equality:

    D_min_n <= D_n <= D_max_n
    G_min_n <= G_n <= G_max_n
    q_mn <= kappa_mn                          for every neighbour m
    D_n = G_n + DeltaG_n + sum_m q_mn          (local energy balance)

Neighbours are coupled by one more constraint, handled at the network
level rather than locally -- the RECIPROCITY constraint:

    q_mn + q_nm <= 0        for every edge (m,n)

and each prosumer's local cost is

    J_n(x_n) = 1/2 a_n*G_n^2 + b_n*G_n + sum_m c_nm*q_mn
               - a~_n*(D_n - D*_n)^2
               |__ generation cost __|  |_trading cost_|  |_ demand-usage benefit _|

with a~_n, a_n > 0. Under the paper's regularity condition
(-b_n/a_n >= G_min_n) the game is monotone and admits a unique
variational equilibrium.


--------------------------------------------------------------------------------
02. BASE DOUGLAS-RACHFORD (lines 3-7)
--------------------------------------------------------------------------------

Split the game's monotone inclusion into two operators: A = pseudo-
gradient + local-box normal cone, B = reciprocity normal cone. The DR
recursion is

    x^(k+1) = x^k + lambda*( J_gA(2*J_gB(x^k) - x^k) - J_gB(x^k) ),
    lambda in (0,2)

Distributed, this becomes five steps per iteration, run independently by
every prosumer with exactly one message exchange:

  line 3  COMMUNICATE. Every prosumer sends each neighbour its own q, and
          receives theirs -- the only place any information crosses
          between nodes.

  line 4  SHADOW. qbar_mn = q_mn - max(0, q_mn+q_nm)/2 -- the exact
          Euclidean projection onto the reciprocity halfspace. D and G
          pass through untouched, since B only constrains trades.

  line 5  REFLECTION. r = 2*qbar - q (again a no-op on D, G).

  line 6  LOCAL PROX. Each prosumer solves its own strongly-convex prox
          by dualising the single local balance equality with a scalar
          multiplier nu, found by bisection -- closed form given nu, no
          communication.

  line 7  RELAXED UPDATE. x^(k+1) = x^k + lambda*(z^k - xbar^k).

Convergence: J_gB = proj_X^rec is firmly nonexpansive, so the DR operator
is (lambda/2)-averaged nonexpansive for any lambda in (0,2) (Lions &
Mercier, 1979) -- it converges to a fixed point whose shadow is the
game's equilibrium.


--------------------------------------------------------------------------------
03. WHY THE PERTURBATION CANNOT BREAK CONVERGENCE
--------------------------------------------------------------------------------

Line 8 adds one term to the update: x^(k+1)_n <- x^(k+1)_n + v^k_n. This
turns the plain DR recursion into a PERTURBED KRASNOSELSKII-MANN
ITERATION. A classical result (Combettes, 2001, building on
Lions-Mercier) states: if T is averaged nonexpansive and
sum_k ||e_k|| < infinity, then

    x^(k+1) = x^k + lambda*(T(x^k) - x^k) + e_k

still converges to a fixed point of T -- the SAME fixed-point set as
unperturbed DR, regardless of what e_k is, as long as it is summable. The
perturbation is built so this holds BY CONSTRUCTION, not by hoping
training keeps it small:

  - both GNN output heads end in tanh -> the raw direction is bounded
    componentwise by 1
  - the confidence gate is a sigmoid, so it can only SHRINK the output
    further, never amplify it
  - the bounded direction is rescaled by a fixed physical reference per
    coordinate (half the D/G box width, the trade capacity kappa) ->
    v^k_n is bounded by a fixed constant of the instance
  - multiplied by a geometrically decaying amplitude scale*rho^k,
    rho in (0,1)

    sum_k ||v^k||  <=  scale * ||physical_scale|| / (1 - rho)  <  infinity

for ANY weights theta -- trained, untrained, or adversarial. This is what
makes it safe to let training run freely: the learned part can only ever
affect SPEED, never correctness.


--------------------------------------------------------------------------------
04. GNN ARCHITECTURE -- Phi_theta
--------------------------------------------------------------------------------

One 1-hop message-passing layer -- spatial depth is capped at one hop to
match the distributed constraint -- plus TEMPORAL recurrence across DR
iterations (not graph hops), which is where most of the network's
effective memory comes from.

NODE FEATURES (8, all strictly local)

  h_D, h_G     position of D_n, G_n in their own box, scaled to [-1,1]
  h_D*         position of the target D*_n in the same box
  h_bal        local balance residual, normalised by the D-box width --
               how far n is from feasible right now
  h_prev_res   how much n's own (D,G,q) moved on the PREVIOUS iteration --
               a direct, self-supervised progress signal ("am I still
               converging here, or stuck?")
  h_a~,h_a,h_b n's own cost-curvature coefficients, min-max normalised
               against FIXED reference ranges declared in the model
               config

  Why fixed ranges, not batch statistics -- a single prosumer cannot
  compute a mean or standard deviation over the whole network -- that
  needs a global reduction, exactly what one-hop communication is built
  to avoid. Normalisation instead uses constants matching the sampling
  ranges of the market generator the training data came from, built
  automatically via GNNConfig.from_market_config(...) so the two can't
  silently drift apart. It's a compile-time constant every node already
  has, not something computed from other nodes' data.

EDGE FEATURES (3), per directed edge (m -> n)

  e_qown    q_mn / kappa_mn -- n's own decision toward m
  e_qrecv   q_nm / kappa_mn -- received from m at line 3 (one-hop,
            already on hand -- no extra round)
  e_c       n's own trading cost c_nm, normalised

MESSAGE PASSING -> RECURRENT UPDATE -> OUTPUT HEADS

    msg_(m->n)   = phi_msg(e_mn)
    agg_n        = (1/sqrt(|Omega_n|)) * sum_m msg_(m->n)
    mem_n^(k+1)  = GRUCell( [h_n^k ; agg_n^k] , mem_n^k )

    gate_n       = sigmoid( phi_gate(mem_n) )                  in [0,1]
    Delta_node   = tanh( phi_node(mem_n) ) * gate_n             -> perturbs (D_n, G_n)
    Delta_mn     = tanh( phi_edge([mem_n ; e_mn]) ) * gate_n    -> perturbs q_mn

  The recurrent memory costs zero communication -- mem_n is PRIVATE,
  per-node state that persists across a prosumer's own dr_step calls;
  nothing about it is ever sent or received, exactly like the local
  iteration counter each prosumer already keeps. It replaced a stateless
  MLP that reacted only to the current instant; with it, the network can
  distinguish "just started pushing here" from "been pushing for 50
  iterations with no visible progress" -- the gate can only learn to use
  that distinction once it exists as an input at all.

  The confidence gate is a purely additive safety margin: gate_n = 0
  recovers plain DR exactly for that node. It can only shrink the
  already-bounded output, so it never affects the summability bound -- it
  just gives the network the structural option to switch itself off when
  uncertain, instead of always committing to a full-strength correction.

TWO EXECUTION PATHS, ONE SET OF WEIGHTS

  Training needs the whole state at once (back-propagation through an
  unrolled trajectory), so it runs CENTRALISED: forward / direction
  vectorise the computation above over the entire graph via cached
  tensors and scatter-aggregation. Deployment is DISTRIBUTED:
  local_forward is exactly what one prosumer runs after communicate(),
  using only its own state, its own memory, and the q it received from
  direct neighbours. Both compute the identical mathematical function of
  the same weights -- cross-checked numerically to agree to about 1e-7
  (see test_gnn_parity.py; iteration counts have been observed to be
  sensitive to floating-point rounding at this scale, e.g. a batched-vs
  -per-neighbour matmul reordering with no logical difference still
  shifted the exact convergence iteration on some instances -- see
  gnn.py's note on `local_forward`'s edge loop -- so this check is kept
  as an actual regression test, not just a one-off manual comparison).

  Every MLP's size depends only on feature counts and the hidden width
  d_h -- never on N or |E| -- so one trained model is architecturally
  deployable on any network size or topology.


--------------------------------------------------------------------------------
05. HOW THE PERTURBATION IS WIRED INTO dr_step
--------------------------------------------------------------------------------

Full amplitude schedule at deployment:

    v^k_n = scale * rho^k * gate_n * tanh(Phi_theta(...)) * physical_scale_n

evaluated on the PRE-UPDATE state (right after line 3), added AFTER the
relaxed DR update commits (line 8). Two pieces of state make this
possible with zero extra communication:

  _round             a prosumer's own count of completed dr_step calls.
                      Because the scheduler calls every prosumer exactly
                      once per synchronous round, this always equals the
                      true global iteration k -- no message needed to
                      know "what round are we on".

  _mem, _prev_residual  the recurrent state described above, plus the
                      node's own residual from the last step -- both
                      private, lazily zero-initialised, reset at the
                      start of a run.

  Train-scale vs deploy-scale -- scale is deliberately allowed to differ
  between training and deployment. Baking a larger scale directly into
  training made results WORSE -- training under bigger, noisier
  perturbation dynamics seems to teach a lower-quality direction.
  Training gently (small scale, stable dynamics) and only AMPLIFYING the
  same learned direction at deployment time works better, and got safer
  once the recurrent memory was added: without it, turning deployment
  scale up caused the worst case to collapse; with it, the worst case
  stays roughly flat as scale increases from 0.3 to 1.0.


--------------------------------------------------------------------------------
06. CENTRALISED TRAINING
--------------------------------------------------------------------------------

Training is the one centralised step, for one reason: back-propagating
through an unrolled trajectory needs the entire state at once, which no
single prosumer has. It produces one set of weights theta, saved to disk
and copied to every prosumer afterwards -- nothing about deployment is
centralised.

The DIFFERENTIABLE ROLLOUT mirrors dr_step line for line, but vectorised
over the whole network -- the vectorised twin of the per-node local prox,
plus the vectorised reciprocity resolvent, playing the role of every
prosumer's local computation at once. The GNN's memory and
previous-residual state are threaded through the unrolled loop exactly as
Prosumer.dr_step threads them across real iterations, zero-initialised at
the first step.

The unroll length K (how many DR iterations are differentiated through
per training step) has to comfortably exceed the amplitude's decay
horizon -- otherwise the loss only ever sees the window where the
perturbation is still active, and never sees the consequences of the
network's own actions once they've decayed away.

07. LOSS FUNCTION -- FOUR ATTEMPTS, IN ORDER
--------------------------------------------------------------------------------

The current loss looks the way it does because of what specifically
failed before it. Worth documenting all four, since the design choices
only make sense in that light.

--- 1. Consecutive-residual log-ratio  [ABANDONED] ---

    L = mean_k[ log(r_k+eps) - log(r_k^DR+eps) ]     r_k = ||xbar^(k+1) - xbar^k||

  EXPLOITABLE. A direction that briefly, nearly freezes the trajectory
  drives r_k -> 0 and log(r_k) -> -infinity -- an unbounded reward --
  while the cost (an unperturbed tail that now has further to go) is a
  bounded, ordinary-sized penalty later. Measured end-to-end: 0.73x --
  slower than plain DR -- despite an excellent-looking training loss.

--- 2. Same idea, windowed to the post-decay tail  [PARTIAL] ---

  Averaging only over k in [k_start, K), past the amplitude's decay
  horizon, excludes the exploitable early window. Helped (-> 1.23x) but
  plateaued: gains concentrated on already-slow outlier instances, while
  roughly a third of ordinary fast-converging instances got worse. Root
  cause survives windowing -- a consecutive-step residual measures how
  far ONE step moved, not how close the point is to the actual solution.

--- 3. Anchored to a precomputed equilibrium  [SET ASIDE ON PRINCIPLE] ---

    ratio_k = d_k / d_k^DR          d_k = ||xbar^k - xbar*||
    L = mean_k[ ratio_k + beta*relu(ratio_k - 1) ]

  Plain DR run to convergence once per training instance (cheap, cached,
  no external labels) gives xbar*. This worked well -- but it IS a
  target-based signal, even though it costs nothing extra and comes from
  the very algorithm being accelerated rather than an external oracle.
  Set aside to keep training strictly self-supervised: no reference
  solution enters the loss, precomputed or otherwise.

--- 4. Self-referential: normalised residual + monotonicity  [CURRENT] ---

    rho_k     = r_k     / (||physical_scale|| + eps)    (SHADOW residual)
    rho_k_aux = r_k_aux / (||physical_scale|| + eps)    (AUXILIARY residual)

    L = mean_k[ rho_k ]  +  gamma_mono * mean_k[ relu(rho_(k+1,aux) - rho_(k,aux)) ]

  No baseline rollout, no precomputed target -- only the perturbed
  trajectory's own residual sequence and a static, zero-computation
  per-instance scale (the same physical reference used to size the
  perturbation itself). Both residuals are measured AFTER v^k is added
  (see training.py's "attempt 5"/"attempt 6" writeup for why measuring
  them before v^k, while theoretically cleaner, was tried and measured
  worse end-to-end).

    decay term         rewards a small normalised SHADOW residual (the
                        quantity the deployment stopping rule actually
                        checks). No log -- driving one rho_k to zero
                        contributes at most a bounded (~0) amount, not an
                        exploitable unbounded one. Unweighted mean over
                        the whole window -- an earlier `late_weight`
                        variant (weighting later steps more) was tried and
                        REMOVED: it did not fix the long-horizon "generic
                        pace" collapse it was meant to address (see
                        training.py / failed_experiments_log.md sec. 1.4,
                        2.7) and is no longer part of the loss.

    monotonicity term   plain DR's own AUXILIARY-iterate residual sequence
                        is the one its convergence theory actually
                        guarantees is non-increasing (a Fejer-type
                        property of averaged operators) -- NOT the shadow
                        residual used above, which is a derived quantity
                        (one extra projection) and is NOT guaranteed
                        monotone even for plain unperturbed DR (measured:
                        ~1 in 6 steps increases on a typical instance). An
                        earlier revision penalised increases of the SHADOW
                        residual instead -- a bug, since it was partly
                        penalising ordinary DR behaviour, not just
                        perturbation damage -- fixed by switching the
                        monotonicity term to the auxiliary residual, which
                        DR's theory really does promise stays flat or
                        drops. Any increase there is now genuine evidence
                        the perturbation broke that property -- exactly
                        the failure mode behind the worst blow-ups seen in
                        earlier, memory-less attempts (one instance went
                        from 353 to 3734 iterations).

  KNOWN LIMITATION, CURRENT DESIGN -- being strictly self-referential,
  this loss has no notion of "how fast would plain DR have solved THIS
  instance". It can teach smoothness and local progress, but cannot
  directly teach "you weren't needed here" -- the leading explanation for
  the pattern in the current results (large wins on structurally slow
  instances, occasional mild regressions on already-fast ones). Several
  follow-up loss designs aimed at this limitation (a pre-perturbation
  fixed-point residual d^k, replacing or supplementing the terms above)
  were tried and reverted -- see failed_experiments_log.md sec. 1.5-1.6
  for the full numbers; none of them is part of the current loss.


--------------------------------------------------------------------------------
08. DATASET CONSTRUCTION
--------------------------------------------------------------------------------

Two-stage, torch-free-first, so instances are cheap to validate, save and
reproduce.

STAGE 1 -- sample_spec(N, seed), pure numpy

  A random connected graph (several topology models available; the
  default interpolates between a random spanning tree at density 0 and
  the complete graph at density 1), then per-node parameters
  (generation-cost coefficients, an operating point, renewable injection,
  a demand box anchored around a feasible point, a target demand), then
  per-edge parameters (trading cost, possibly asymmetric; capacity,
  symmetric per undirected pair).

STAGE 2 -- build(spec, seed)

  Turns the numeric spec into real Prosumer/EnergyNetwork objects. A
  separate seed draws the INITIAL decision variables (D, G, q) inside
  their boxes -- the starting point x^0, independent of the spec itself.

REPRODUCIBILITY AND TRAIN/TEST DISJOINTNESS

  Instance i of a dataset always uses seed = cfg.seed*100003 + i -- a
  function of its own index alone, never of how many instances are
  requested in total. Growing a dataset only ever APPENDS new instances;
  it never reshuffles the ones already drawn. Splitting into train/test
  is a plain sequential partition of that list -- by construction, the
  two never overlap. In practice, when the training pool needs to grow
  independently of the test pool, the extra training instances are drawn
  from a DISTINCT seed offset entirely, rather than by extending the same
  sequential draw -- otherwise growing training would silently shift
  which instances land in the test set and break every before/after
  comparison.

  During training, x^0 is redrawn fresh for every (instance, epoch) pair,
  so the network is never fit to one arbitrary starting point. During
  evaluation, x^0 is fixed per test instance, so comparisons stay
  reproducible run to run.


--------------------------------------------------------------------------------
09. END-TO-END PIPELINE
--------------------------------------------------------------------------------

  01 DATASET     MarketConfig -> sampled specs -> train / test split,
                 disjoint by construction
       |
       v
  02 INIT Phi_theta   PerturbationGNN with random weights, feature ranges
                      bound to the market config
       |
       v
  03 TRAIN       Per epoch, per instance: fresh x^0, differentiable
                 K-step rollout, self-referential loss, Adam step
       |
       v
  04 SAVE theta   Weights + both configs persisted to disk -- the only
                  artifact deployment needs
       |
       v
  05 DEPLOY      Every prosumer gets a LocalAgent(theta, rho, scale) --
                 inference is now 100% distributed
       |
       v
  06 EVALUATE    Real distributed solver, with vs. without Phi_theta, on
                 held-out instances -- iterations to tolerance

Only step 03 is centralised. Step 06 is the only number that counts --
never the training-time rollout.

10. CURRENT RESULTS
--------------------------------------------------------------------------------

NOTE: this section previously reported a 2.45x mean speed-up figure that
predates a real bugfix (the monotonicity term was measured on the wrong
residual -- shadow instead of auxiliary, see sec. 07 item 4) and the
removal of `late_weight`. It is NOT comparable to the numbers below and
should not be cited. failed_experiments_log.md is the authoritative,
continuously-updated record of what has and hasn't worked; this section
only summarises the currently validated configuration.

Validated configuration (gamma=2.0, lambda=1.0, bisect=25; GNN with GRU
memory + confidence gate, rho=0.9, unroll=400 in training, no TBPTT;
40 epochs, constant lr=3e-3; self-supervised two-term loss, gamma_mono=2.0
-- see sec. 07 item 4), evaluated in the real DISTRIBUTED solver:

  Dataset                                          Mean speed-up
  --------------------------------------------------------------
  Variable graph/parameters, N=10, density=0.3      2.12x
  (30 held-out test instances)
  Fixed graph, N=10, density=0.7, denser            1.23x
  (10 held-out test instances)

Both numbers sit below the 2.45x figure previously (incorrectly) reported
here. The open problem is the minority of regressions, which are NOT the
instances that are structurally hard for plain DR (those improve the
most, sometimes 10-20x) -- they cluster on instances plain DR itself
already solves quickly. There, the perturbation's active window overlaps
almost the entire natural trajectory rather than just nudging its start,
and a badly-calibrated push can cost more than it saves.

Leading hypothesis (STILL OPEN as of this writing): the amplitude
envelope scale*rho^k is identical for every instance regardless of how
much help it actually needs, and the training signal is likely dominated
by slow/plateau instances -- their residual stays far from zero across
far more of the unrolled window, generating much larger gradients than an
instance that's basically already converged early. Six loss redesigns and
eight attempts to extend the perturbation's effective horizon (rho/unroll)
have been tried against this -- ALL either reverted or shelved, see
failed_experiments_log.md for the complete numbers. Re-examine that log
before proposing a new variant of either lever.

CONFOUND FOUND AND RE-TESTED: gamma and lambda were tuned once, on the
N=10/density=0.3 dataset only (sec. 11 below), and reused unchanged on
the denser N=10/density=0.7 dataset. A direct check of PLAIN DR (no GNN
at all) on that denser dataset's 10 test instances found 1/10 fails to
converge within the 20000-iteration cap at gamma=2.0, while gamma=1.0
(same lambda, same bisect) converges on all 10 (at the cost of roughly 2x
more iterations on the instances that already converged easily).

Retrained the full pipeline (same architecture/loss/schedule as the
validated recipe -- only gamma changed, 2.0 -> 1.0) on this corrected
baseline. Result: mean speed-up 1.23x -> 1.25x, essentially flat. The
previously non-convergent instance (#4) now converges reliably under
BOTH plain DR and DR+Phi_theta (6321 vs 7664 iterations) instead of
tying at the 20000 cap -- a real robustness fix, no longer an artefact
diluting the mean -- but the learned perturbation is still SLOWER than
plain DR there (0.82x), and 4/10 instances regress overall (0.47x, 0.82x,
0.57x, 0.95x). So: the gamma confound was real and worth fixing (it
removed a meaningless 1.00x tie and a non-convergent baseline from the
comparison), but it is NOT the dominant explanation for the regression
pattern -- that credit still goes to the self-referential loss's known
limitation above (loss dominated by slow/plateau instances). Re-tuning
gamma is a correctness/hygiene fix to make the measurement trustworthy,
not a fix for the open problem itself.

DIAGNOSTIC (refines the "known limitation" above): measured directly on
the gamma=1.0 model -- for each of the 10 test instances, the point k
where the TRAINING rollout's shadow residual first drops below 1% of its
own k=0 value (a proxy for "how much of the unroll=400 window is still
gradient-informative for this instance") is 24-95 steps at deploy_scale,
with NO visible correlation to whether that instance ends up winning or
regressing in the real distributed comparison -- e.g. instance #1 (which
regresses to 0.47x) and instance #6 (which improves to 1.64x) both bottom
out at k=24 in the simulated rollout. So the regression pattern is not
simply "fast instances get a shorter/weaker gradient signal than slow
ones" -- ALL instances get a similarly short informative window (a small
fraction of the 400-step unroll), because plain DR's REAL convergence
horizon on this dataset (639-6321 iterations at gamma=1.0) is up to ~15x
longer than what training ever unrolls through. This reframes the
limitation: it looks less like a per-instance loss-weighting problem
(which a renormalisation, e.g. by the rollout's own r_0 instead of the
fixed physical_scale, would address) and more like the SAME root cause
already identified in the rho/unroll extension attempts (sec. "ATTEMPTS
TO EXTEND REACH" in example_l2play.py) -- training simply never observes
the part of the trajectory, beyond k~100-400, that determines a hard
instance's real outcome. A per-instance normalisation constant only
rescales the loss curve's height, not WHERE in k it stops being
informative, so on its own it is not expected to fix this.

FOLLOW-UP TESTED AND FAILED (see failed_experiments_log.md sec. 2.9 for
full numbers): a natural next idea from the diagnosis above -- replace
the geometric decay rho^k with a slower but still summable schedule
(polynomial, a_k=(k+1)^-poly_p, poly_p=1.1; Combettes' theorem only needs
ANY fixed summable sequence, not specifically geometric), combined with
TBPTT to reach unroll=2400 -- was implemented (gnn.GNNConfig now supports
decay="polynomial" alongside the original "geometric") and trained end to
end on the gamma=1.0 corrected baseline (5.2h training + 0.5h evaluation).
Result: WORSE, uniformly -- all 10/10 test instances regressed (0.07x to
0.65x, mean 0.27x), a qualitatively different failure pattern than every
other experiment in this document (which always showed a MIX of
improved/regressed instances). Root cause, confirmed by inspecting the
worst instance's actual residual trajectory: not the "freezing" exploit
(residual reaches near the tolerance on schedule, as fast as plain DR
would), but a stall in the FINAL approach -- thousands of iterations
hovering just above the 1e-6 tolerance (even ticking up slightly at one
point) where the geometric model on the SAME instance completes a clean
descent to convergence in under 100 iterations. Combettes' theorem
guarantees eventual convergence for any summable perturbation but says
nothing about the RATE near the fixed point; DR's own unperturbed
terminal approach is a clean, fast (roughly geometric) contraction, and
ANY polynomial decay is asymptotically slower than any fixed geometric
rate, so for k large enough it inevitably becomes the dominant, still-
non-negligible term right where DR would otherwise be finishing cleanly.
This is not a bad choice of poly_p -- a larger p only pushes the same
interference further out, it does not remove it. Combined with the
rho/unroll-extension family's failure (gradient credit diluted over long
BPTT), this closes off "extend the perturbation's active lifetime" as a
viable lever along BOTH axes tried so far (raise the geometric rate;
change the decay family), not just this one specific configuration.

CLUSTERED (more realistic) DATASET, VALIDATED RECIPE UNCHANGED: every
result above draws each instance's market parameters as an INDEPENDENT
sample over the whole MarketConfig range (`DatasetConfig`) -- instances
are maximally heterogeneous, unlike a real deployment (one physical grid,
a handful of typical operating regimes, small day-to-day variation
within each). `market_generator.ClusteredDatasetConfig` /
`build_clustered_datasets` (example_clustered.py) instead draws
N_REFERENCES=5 reference markets (graph fixed, as before) and expands
each into perturbed instances by jittering the reference's own
PRIMITIVES (not the derived box/balance quantities directly, which could
break the regularity condition -- see `MarketPrimitives`'s docstring) by
+/-10%, independently for train (10/reference = 50) and test
(2/reference = 10, disjoint draws, same references -- an interpolation
test: new day-to-day variation on a market character already seen, not a
new market character). Same validated recipe (gamma=1.0, geometric
rho=0.9, unroll=400, no TBPTT) -- only the dataset structure changed.
Result: mean speed-up 1.42x (vs 1.25x on the iid dataset), 7/10 instances
improved (up to 4.36x), 3/10 regressed (down to 0.34x) -- same MIXED
pattern as every other successful run in this document (unlike the
uniform 10/10 failure in the polynomial-decay experiment above), just a
somewhat better mean. Plausible reading: with only 5 underlying market
characters instead of an unbounded iid range, training instances within a
cluster are much more similar to each other, giving a cleaner, less noisy
per-cluster signal -- but note this is still only a 10-instance test set
(recurring pattern 6: noisy), and the interpolation setup (same
references in train/test) is an easier generalisation target than the
fully iid case by construction, so the two numbers are not a strict
apples-to-apples comparison of "harder vs easier data" alone.

COST-GAP-TO-J* LOSS TERM (new): `training.stability_loss` gained an
optional third term, OFF by default (`TrainConfig.loss_gamma_cost=0.0`
reproduces the loss above exactly):

    gamma_cost * mean_k[ |J(xbar^k)-J*| / (|J(xbar^0)-J*|+eps) ]

DELIBERATELY not strictly self-supervised (uses J*, `equilibrium_qp.
solve_equilibrium_qp` -- an exact QP solve, milliseconds, cached once per
instance across all epochs since J* does not depend on the epoch-varying
x0). This does NOT weaken deployment safety: J* never enters inference,
and Theorem 1 holds for any theta regardless of how it was trained.

Design reasoning (see `stability_loss`'s docstring for the full version):
J* (not a specific equilibrium point, "attempt 3"'s anchor) because the
game is a potential game and every v-GNE shares the same J*, so this does
not penalise converging to a different-but-valid equilibrium. Absolute
value, not one-sided: measured directly on trained models, J(xbar^k)
UNDERSHOOTS J* by 40-54% on every test instance, under PLAIN DR too (the
balance equality is not enforced pointwise on intermediate iterates) -- a
one-sided term would have rewarded exactly that undershoot, reopening
"attempt 1"'s exploit in a new guise. Normalised by the rollout's OWN
starting gap |J(xbar^0)-J*|, not by |J*|: measured directly, raw cost-gap
magnitude does not scale with |J*| (one instance had J*=2.98 with gap up
to ~69, another J*=12.10 with gap ~40), so dividing by |J*| would weight
instances by an accident of their parameter draw, not by how hard they
are. Kept at a SMALL weight relative to loss_gamma_mono by design: the
trading-cost term is LINEAR in q, so cost alone under-determines where
the trade variables should sit -- meant as a secondary nudge alongside
the residual term (no such blind spot), not a replacement for it.

RESULT (gamma_cost=1.0, clustered dataset, gamma=1.0 baseline, otherwise
identical to the run above -- example_clustered_costgap.py): mean
speed-up 1.37x, essentially flat to SLIGHTLY BELOW the 1.42x without the
term. But the mean alone is misleading here -- the full distribution
moved in a way directly relevant to this project's actual goal (reliable
improvement, not just a higher average):

  metric                    without cost-gap   with cost-gap
  ----------------------------------------------------------
  mean                            1.42x             1.37x
  median                          1.18x             1.33x   (better)
  std across instances            1.04              0.42    (less than half)
  worst case                      0.34x             0.71x   (much better)
  best case                       4.36x             1.99x   (worse)
  instances regressed (<1x)       3/10              2/10

Per-instance, three previously-regressed instances flipped to solid wins
(0.74x->1.36x, 1.00x->1.99x, and the single worst case in the whole
project so far, 0.34x->1.96x), while two previously-good instances
weakened (1.40x->1.00x, 1.27x->0.86x) and the single standout win shrank
substantially (4.36x->1.68x). 5/10 instances changing category on a
10-instance sample is itself a flag (recurring pattern 6: noisy) -- see
the confirmatory re-run below before trusting this table.

CONFIRMATORY RE-RUN (verify_costgap_30.py): re-evaluated BOTH already-
trained checkpoints (no retraining -- this is a measurement question, not
a training one) on a FRESH 30-instance test set drawn from the SAME 5
references, so the two models are compared on identical, larger data:

  metric                    without cost-gap   with cost-gap
  ----------------------------------------------------------
  mean                            2.914             2.055
  median                          1.363             1.471   (confirmed better)
  std across instances            7.156             2.855   (confirmed: less than half)
  worst case                      0.350             0.370   (NOT confirmed -- a wash)
  best case                       41.012            16.696  (confirmed: compressed a lot)
  instances regressed (<1x)       9/30              7/30    (confirmed, modestly)

The 10-instance table's "worst case improves a lot" (0.34x->0.71x) does
NOT hold up at n=30 -- the true worst case is statistically a wash (0.35
vs 0.37), just landing on a different instance each time (the original
worst instance flips to one of the best; a different, previously-fine
instance becomes the new worst, 0.50x->0.37x). That was a coincidence of
which outlier happened to land in the 10-instance draw, not a real effect
of the loss term. What DOES hold up, more clearly than the small sample
suggested: median improves, variance drops sharply, regression count
drops modestly -- driven mainly by the term compressing a heavy right
tail (the without-cost-gap distribution has instances up to 41x), not by
rescuing the worst instances. Revised reading: the cost-gap term makes
the TYPICAL outcome more predictable (higher median, much lower spread),
at a real (not negligible, ~29% relative here) cost to the mean -- but it
is NOT a fix for the worst-case-regression problem this project set out
to solve; that remains open. Whether the median/variance improvement is
worth the mean cost is a judgement call, not something the numbers settle
outright.

DEPLOY-TIME AMPLIFICATION TESTED AND REJECTED (verify_scale_amplification.py):
motivated by wanting the perturbation to have MORE effect (push cost
closer to J*), tried simply deploying the ALREADY-TRAINED cost-gap model
at a higher amplitude than the validated DEPLOY_SCALE=1.0 -- 1.5 and 2.0
-- no retraining, same 30-instance test set as the confirmatory re-run
above (so directly comparable). Summability stays finite for any scale
(Theorem 1 unaffected), so this was a pure effectiveness question, not a
safety one.

  metric          scale=1.0   scale=1.5   scale=2.0
  --------------------------------------------------
  mean               2.055       1.870       1.895
  median             1.471       1.338       1.273
  min                0.370       0.330       0.319
  max                16.696      12.604      15.199
  regressed           7/30        7/30        7/30

scale=1.0 wins on EVERY metric; median declines monotonically as scale
increases (1.471 -> 1.338 -> 1.273, a clean trend, not noise). Reading:
this is a DIRECT, decisive negative result for "just turn up the volume."
Consistent with the earlier d^k diagnostic (the gate does not yet
discriminate well between "DR needs help right now" and "DR is already
fine") -- amplifying an indiscriminate policy amplifies the noise along
with any genuine help, and here the noise dominates. This does NOT rule
out gamma_cost increases (a training-time lever that reshapes WHAT the
policy learns, not just how loud an already-fixed policy is played) --
those remain untested at this weight and are a different kind of change.
Lesson for this project: "more effect" achieved by raw amplitude is not
free -- effectiveness here is bottlenecked by the POLICY'S precision, not
by how much room it is given to act.
